# 降低 WE 壁纸 CPU 开销 · 方案与实测依据

- 日期：2026-10-20
- 对象：`myprojects/星语心恋S8`（13 层 = 4 texture + 6 spine + 3 particle），2560×1600，WE 全局 `fps:30`
- 前置结论见 `REPORT_GPU渲染归属_2026-10-20.md`：渲染在核显硬件路径上，瓶颈是 **CPU 侧每帧提交**，不是光栅化，换独显零收益

---

## 勘误（2026-10-20 23:45，必读）

本文与 `REPORT_GPU渲染归属_2026-10-20.md` 里所有 **WE 侧 CPU 百分比都虚高约 4.2 倍**，原因是采集脚本的分母写错：

- 采样循环是「`Start-Sleep 1s` → 读 CPU 累计时间 → `Get-Counter '\GPU Engine(*)'`」；
- 实测那条**全表**查询单次要 **3.2 s**（上千个实例），即相邻两次 CPU 读数实际跨约 **4.2 s**，脚本却按 1 s 作分母；
- 所以 `CPU% × 4.2 ≈ 真实值`。GPU3D 那一列取自计数器瞬时值，**未受影响**。

交叉验证：23:09 那次报的 `51.7 / 65.2` ÷4.2 = `12.3 / 15.5`，与同一进程的生命周期均值 `11.0 / 14.1`、以及修好后的两次窗口 `9.4~10.4 / 12.5~13.5` 全部吻合。

**修正后的真实量级**（2560×1600、30fps、13 层）：

| 口径 | 旧（虚高） | 真实 |
|---|---|---|
| gpu-process + renderer | 20.9 ms/帧、0.68 核 | **7.3~8.0 ms/帧、≈0.23 核** |
| 整机占比（16 线程） | ~4% | **≈1.4%** |

因此下文「2 档差 3 倍」的**比值**仍成立（同一分母），但**绝对量级要下调 4 倍**：不是「0.7 核 ↔ 1.5 核」，而是「≈0.15 核 ↔ ≈0.35 核」。采集工具已修（`_regress/gpu_stat.ps1`：Stopwatch 真分母 + 定向实例查询，每样本 1 s），其余四个带缺陷的脚本已删除。

## 0. 先说一个关键事实：这份壁纸的 CPU 开销有 2 档

> 下表的 CPU 列取自**修复前**的脚本（虚高约 4.2 倍），只用于比较**比值**；真实绝对值见上方勘误。

| 状态 | gpu-process（虚高） | renderer（虚高） | 真实合计 | GPU3D | 每帧 GPU 忙时 |
|---|---|---|---|---|---|
| 限帧 30fps（正常） | 28.5% | 34.2% | ≈0.15 核 | 23.3% | 7.8 ms |
| 重载后（约 90fps 自由跑） | 77.2% | 74.5% | ≈0.35 核 | 70.6% | 8.5 ms |
| 23:39 重载后稳态（修复后实测） | 9.4~10.4% | 12.5~13.5% | ≈0.23 核 | 28.8~29.0% | 8.7 ms |
| 暂停 | 0.3% | 1.7% | 0% | 0 |

两点可直接读出：

1. **暂停即归零** ⇒ 没有任何「固定每帧合成开销」，全部成本随帧产生。压帧率/压每帧工作量**线性见效**，不存在压不动的底噪。
2. **两档的「每帧成本」几乎相同（8~9ms/帧）**，变的是每秒帧数（约 3 倍）⇒ 重载后不是场景变重，而是**帧率上限没生效**。

### 为什么上限会丢

`src/weFps.ts`：WE 不替页面限帧，只通过 `applyGeneralProperties({fps})` **推**一个值过来（官方《FPS Limiter》原文 "the page has to honour it"）。本工程的回落链是：

```
收到过 WE 信号 → 用 WE 的值
从没收到过     → config.maxFps（本工程没写 ⇒ 0 ⇒ 不限帧）
```

页面重载后 JS 状态清零（`hasFps=false`），若 WE 不再推一次，就永久退回「不限帧」。重载前能跑到 30fps，是因为那一次启动时 WE 推过。实测重载后连跑 60s，一直停在 ~70% 没有回落 ⇒ 期间没有补推。

> 判定依据：粒子侧撑不起 3 倍填充——两组 1000 上限的系统实际稳态只有约 100 个 200px 级粒子（合计约 0.5 屏 overdraw），而 GPU 忙时从 7.8ms 只变成 8.5ms/帧。所以变量是帧数，不是场景量。
> 10 秒可自证：WE 设置 → 性能 → 帧率限制 从 30 改成 60 再改回 30（强制重推）。若 CPU 立刻掉回 ~0.35 核，即为此因。

## 1. P0：改配置就生效（不需重新构建）

| # | 改动 | 落点 | 实测/预期收益 |
|---|---|---|---|
| 1 | 补 `"maxFps": 30` | 工程 `assets/config.json` | 堵住"重载后不限帧"这个洞，直接砍掉那 3 倍（1.5 核 → 0.7 核） |
| 2 | 加 `"idleFps": 10` + `"idleAfterSec": 20` | 同上 | 闲置 20s 后压到 10fps ⇒ 比 30fps 再省约 2/3。**日常挂着壁纸用电脑时最大的一笔** |
| 3 | WE 全局 帧率限制 30 → 24 | WE 设置 → 性能 | 线性 −20%（0.7 核 → 0.56 核）；待机动画 24fps 观感损失很小 |

代码侧已支持 `idleFps`（`index.ts` 2629-2641，每帧读、改动即时生效），本工程只是**没配**。判据只看鼠标，不看自动事件，所以不会因为待机演出而失效。

## 2. P1：代码级热点（收益明确，需改代码）

### 2.1 粒子：整块缓冲上传 + 空系统也在重建

`ParticleAnimator.buildGeometry()` 每帧结尾无条件做：

```ts
this.posAttr.needsUpdate = true;   // × 5 个属性
...
this.geometry.setDrawRange(0, n);
```

`needsUpdate = true` 且**不设 `updateRange`** ⇒ three.js 上传的是 `maxNumParticles` 尺寸的整块缓冲，与实际活跃粒子数无关。本工程：2 组 × 1000 + 1 组 × 10 ⇒ 每帧约 15 次全量上传、约 0.3 MB/帧（≈9 MB/s），而其中两组长期只有 0～100 个粒子。

改法（两处，都很小）：

1. 上传范围按活跃顶点数收窄：
   ```ts
   this.posAttr.updateRange = { offset: 0, count: n * 3 };
   ```
   （各属性按自己的 itemSize：position 3 / uv 2 / aMaskUv 2 / aAlpha 1 / aStartCol 4）
2. 空系统早退：`particles.length === 0 && 上一帧也为 0` 时直接 `return`，不重建几何。

### 2.2 骨架合批：每个 slot 每帧重算 program cache key

submodule `threejs-spine-3.8-runtime-es6/core/src/threejs/SkeletonMesh.ts:320`：

```ts
batchMaterial.needsUpdate = true;   // 每个 slot、每帧，无条件
```

`needsUpdate` 会让 `material.version++`，three.js 每帧重走 `getProgram()` → `getProgramCacheKey()`（旧 profile 里该项 self-time 占 3%）。6 个骨架 × 多 slot，每帧几十次。

改法：把该行移进上面「texture 真的换了」的分支里（`batchMaterial.uniforms.map.value != texture.texture` 时）才置 true。

> 这是 git submodule，改动需单独提交并在主仓更新指针；属于"该上游修"的问题，建议先本地试，确认收益再决定是否 fork。

## 4. 不要做的两件事

1. **不要换独显渲染**。30fps 时 GPU 只忙 23%，不是瓶颈；且 WE 官方明确要求壁纸与桌面同卡，跨卡要经 CPU 搬图，只会更慢更热。
2. **不要指望 WE 的暂停规则**。它只认全屏/最大化/焦点，窗口化用电脑时永不触发——这正是 `idleFps` 存在的理由（`index.ts` 2610 附近注释已记录这个坑）。
