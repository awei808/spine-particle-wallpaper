# WE 壁纸 CPU 占用 · 定量实测报告（真机，非软渲染）

- 日期：2026-10-19
- 环境：**真实 Wallpaper Engine 2.0.8**（`webwallpaper64.exe` CEF 渲染进程），壁纸 = `星语心恋S8`
- 机器：16 逻辑核，屏幕 2560×1600 @150% 缩放
- 方法：进程 CPU 时间差分（`Get-Process.CPU`）→ 单核% / 整机%；按 PID 归因到 renderer / gpu-process；A/B 通过换 bundle、改 config、`-control closeWallpaper + openWallpaper` 重载
- 脚本：`_work_CPU实测/10_采样.ps1`、`13_Top进程.ps1`、`15_按PID采样.ps1`、`14_改配置.py`

---

## 1. 结论（一句话）

**壁纸的稳态成本只有 0.76~1.14 核（整机 5~8%），但它每 5~6 秒会爆一次 3~4.5 核，把整机顶到 90~99% —— 这就是"50~100% 跳"的真相。**
把帧率压到 30fps 后，爆发消失、中位数砍半。**单独关 MSAA 无效（反而更忙）**。鼠标移动/拖尾只占 8~28%，不是主因。

### 2.1 三个干净的 A/B（同轮次、只变一个因素）

| 对比 | 变量 | core 中位变化 | 判读 |
|---|---|---|---|
| **E1 → E2** | 只加 `maxFps:30` | **113.5 → 50.2（−56%）** | ★★★ 限帧是唯一硬杠杆，峰值 368→103（−72%） |
| C1 → C2b | 只让鼠标动 | **76.0 → 97.5（+28%）** | 鼠标移动有成本，但不是主因 |
| F1 → F2 | 30fps 下让鼠标动 | **50.3 → 54.2（+8%）** | 帧率减半后交互成本也减半 |
| C1 → E1 | 只关 MSAA（仍无限帧） | **76.0 → 113.5（+49%）** | ⚠️ **关 MSAA 反而更忙**（补帧效应） |

> ⚠️ D1b（关拖尾）看起来比 C1 更贵，但它是**重载后另一轮**、且窗口里恰好赶上 4 次爆发
> ⇒ **不能**据此说"关拖尾更贵"。拖尾的真实成本看 F1 vs E2：50.3 vs 50.2 ⇒ **静止时≈0**；
> 只有鼠标真的在动时才有（F2 比 F1 多 4 个点）。

## 3. 关键发现

### 3.1 ★★★ 周期性爆发：每 5~6 秒一次，3~4.5 核

按 250ms 采样、按 0.5s 分桶后，峰值的形状很固定：

```
旧包 60fps：t=3.7s → 455% core（4.5 核）/ sys 81%
            t=11.5s → 391% core          t=15~17s → 189~309% core
30fps：     全程 30~80%，唯一一次 102.9%（1 核）
```

**爆发期正好对应采样循环被饿**（采样间隔从 0.5s 被拉到 1.4~2.4s），说明是真实的全系统压力，不是统计伪影。

### 3.2 ★★★ 不是"GPU 应该干却没干"：这台机器上 CEF 就是软件渲染

**直接证据**：播放态下同步采 8 秒 Windows GPU Engine 计数器 ——

```
t=1..8s   3D 引擎利用率 = 0.0%（每一秒都是 0）
copy 引擎利用率 = 0.0%
同期： renderer = 264.8% 单核    gpu-process = 237.3% 单核
```

而同一时刻 **WorkBuddy 的 3D 引擎利用率是 27.9%**（同机同计数器有值）
⇒ 不是计数器失灵，是 **WE 的 CEF 完全没有向 GPU 提交图形工作**。

**为什么名字叫 `gpu-process` 却在算像素**：Chromium 的 `--type=gpu-process` 是"GPU 服务进程"，
它同时承担**软件光栅化**（`--num-raster-threads=4` 就在 renderer 的命令行里）与命令缓冲/纹理上传。
GPU 加速不可用时，像素运算就落在这个进程的 CPU 线程上 —— 名字不变，负载全在 CPU。

按 PID 拆 31.7 秒（旧包、静止）：

| PID | 角色 | 该段 CPU | 平均 |
|---|---|---:|---:|
| 17592 | **renderer** | 16.77 s / 31.7 s | **52.9% 单核** |
| 19224 | **gpu-process** | 16.56 s / 31.7 s | **52.2% 单核** |
| 23436 | utility | 1.28 s | 4.0% |
| 28068 | main | 0.70 s | 2.2% |
| 其余 3 个 | network/storage/audio | ≈0 | ≈0 |

**结论**：这不是"我们的代码把活儿推给 CPU"，而是 **WE 的 CEF 在这个环境下没有 GPU 光栅**
（`--gpu-preferences` 是 WE 传的二进制偏好，页面侧无法改；`--force-device-scale-factor=1` 也在）。
所以我们能控制的只有两件事：**每帧多少像素**、**每秒多少帧**。而实测证明 —— **只有后者有效**（见 §3.6）。

### 3.3 ★★ 鼠标在**别的窗口里**移动，壁纸照样响应

C1（静止）76.0 → C2b（鼠标在 WorkBuddy 窗口内画圈）97.5，**+28%**。
⇒ 壁纸确实收到了被窗口覆盖区域的鼠标事件（WE 用宿主侧鼠标转发，CEF 侧又禁用了遮挡检测，见 §3.5）。
但这条链路的绝对量级只有 **+0.2 核**，即使完全不管，也解释不了 90% 的整机占用。

### 3.4 ★★ 整机占用是"叠加"出来的，不是壁纸一个人

同一时刻的 Top 进程（10 秒差分）：

| 进程 | 单核% | 整机% |
|---|---:|---:|
| WorkBuddy（4 个进程合计） | 275.2 | **17.2** |
| webwallpaper64（renderer+gpu） | 93.7 | **5.9** |
| audiodg（音频） | 12.6 | 0.8 |
| AMD/NVIDIA/Steam/Edge/PresentMon… | ~25 | ~1.6 |
| **合计** | ~440 | **≈27.5** |

⇒ "打开编辑器 + 壁纸"的 45%（中位）里，**编辑器自己占 17 个点，壁纸只占 6 个点**，其余是后台。
爆发期的 90~99% 则是"壁纸 4.5 核 + 编辑器 2.75 核 + 后台 1.5 核"叠出来的。

### 3.5 平台层已确认的两个"永不让路"开关

`webwallpaper64.exe` renderer 的命令行（实测读出）：

```
--disable-background-timer-throttling
--disable-features=...,CalculateNativeWinOcclusion,WebContentsOcclusion,...
--force-device-scale-factor=1  --device-scale-factor=1
--num-raster-threads=4
```

- **`CalculateNativeWinOcclusion` / `WebContentsOcclusion` 被显式禁用**
  ⇒ 被窗口盖住时 **Chromium 不会认为自己不可见** ⇒ rAF 不会因遮挡降频；
- **`--disable-background-timer-throttling`** ⇒ 后台定时器也不降频；
- **`--force-device-scale-factor=1`** ⇒ `window.devicePixelRatio` 恒为 **1**
  ⇒ `dpr:"auto"` 恒解析为 **1.0**（不是上一轮假设的 1.5）；
  但 **`dpr` 显式写数字仍然有效**（它走 three 的 `setPixelRatio`，与 `devicePixelRatio` 无关，见 §3.6 实测）。

### 3.6 ★★★ 补帧效应在真机上复现了三次：**单独降"每帧成本"一定失败**

| 改动 | 每帧工作量 | 实测 core 中位 | 结果 |
|---|---|---|---|
| 基线（MSAA 开、dpr=1.0、无限帧） | 100% | 76.0 | — |
| 关 MSAA（无限帧） | ≈80% | **113.5** | **+49%（更忙）** |
| `dpr=0.75`（像素 ×0.56，无限帧） | ≈56% | **≈150**（本轮 16 点中位） | **更忙** |
| 关 MSAA + **`maxFps:30`** | ≈80% × 30fps | **50.2** | **−56%** |

**机制**：rAF 没有上限时，单帧便宜了 ⇒ Chromium 就用**更多帧**把省下的时间填满
⇒ 瞬时 CPU 不降反升。**只有给帧率设上限，"每帧成本"的收益才会体现为 CPU 下降。**
这条在 headless（上一轮）和真机（本轮）都成立，是这套壁纸最重要的性能规律。

## 4. 为什么表现为"50~100% 跳"

```
稳态：0.76~1.14 核  →  整机 36~53%（编辑器 17 + 壁纸 6 + 后台 15）
爆发：3~4.5 核       →  整机 81~99%（每 5~6 秒一次，持续 1~3 秒）
```

爆发的触发点无法从进程外部定位到具体函数（没有 CDP 通道，WE 覆盖了 `cefcommandline`，调试端口没开），
但**它与帧率强相关**：60fps 下必然出现，30fps 下消失（33 个采样点里仅一次 102.9%）。
最可能的机制是"每帧的顶点/纹理上传 + 光栅任务在 GPU 进程侧排队，周期性地一次性排空"，
这也与 §3.2 的 gpu-process 半核吻合。

## 5. 建议（按实测收益排序）

| # | 动作 | 实测收益 | 代价 |
|---|---|---|---|
| **1** | **部署 10-19 的 bundle + 给 S8 的 config 加 `"maxFps": 30`** | 中位 **−56%**，峰值 **−72%**，爆发消失 | 动作/粒子从 60 降到 30fps；⚠️ S8 缺 `assets/events.jsonc`，换新包后事件全空，**必须先补文件** |
| **2** | WE 性能页「其他应用程序**获得焦点**时」= 暂停 | 用编辑器时壁纸 → 0（实测暂停态 0.0 核） | 点开任何窗口壁纸就停，回桌面立刻恢复 |
| 3 | 空闲降帧（8~15s 无交互 → 20fps） | 介于 1 与 2 之间（未单独测） | 需改代码 |
| 4 | 实现 `applyGeneralProperties`，接 WE 的 `fps=30` | 与 1 同效，但让用户在 WE 里自己调 | 需改代码 |
| ❌ | **单独关 MSAA** | **实测 +49%（更忙）** | 不要单独做；与限帧一起做才有意义 |
| ⚠️ | **`dpr: 0.75`**（像素 ×0.56） | 单独做**更忙**（补帧）；限帧后才有净收益 | 清晰度下降；`auto` 在 WE 里恒为 1.0，写数字才生效 |
| ❌ | 关拖尾 | 静止时≈0，只在鼠标动时省 ~0.04 核 | 不值得为 CPU 牺牲效果 |

**最小可落地组合**：① 给 S8 补 `events.jsonc` ② 换新 bundle ③ config 加 `"maxFps": 30`
⇒ 预期整机从 36~53%（峰值 99%）降到 **27~31%（峰值 62%）**。

## 7. 诚实标注

- 这台机器上 WorkBuddy 本身在跑（占 2.75 核），会抬高每轮"整机%"的绝对值；
  **跨轮次比较请用 `core 中位`（WE 单核）**，整机%只用于说明叠加效应。
- 爆发的外部成因（GC / 光栅排队 / 驱动）**没有定位到函数级**：WE 的 `cefcommandline` 被它自己的
  `--enable-media-stream` 等参数覆盖，`--remote-debugging-port` 未生效，无法在页面内插桩。
  若要进一步定位，需要给 S8 装一个"自测版 bundle"（把计数器写进 `document.title` 或页面上）再截图读。
- **GPU 3D=0 的判读**：同一秒内同机 `WorkBuddy` 的 3D 引擎利用率是 27.9%，
  说明计数器本身在工作；`copy` 引擎也是 0，基本排除"换了别的引擎类型"。
  但**软件渲染可能是本机环境导致**（多显卡 / 驱动 / WE 的 GPU 偏好），
  换一台机器不保证复现 —— 所以结论写成"这台机器上 CEF 是软件渲染"，而不是"WE 一律软件渲染"。
- 30fps 组的"事件全空"是因为 S8 缺 `events.jsonc`（新包无 fallback）；这只影响触摸/问候，
  **不影响渲染循环**，因此 CPU 对比仍成立（且事件为空会略微**低估**旧包的 CPU）。
