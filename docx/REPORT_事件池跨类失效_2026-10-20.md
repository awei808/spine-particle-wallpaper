# 回归报告：「事件池」通道类别跨选静默失效

- 日期：2026-10-20
- 现象来源：用户报告（内置设置 → 事件池 → 三个入口的「可触发的事件」多选）
- 结论：**不是面板没存进去，是引擎漏斗把跨类选择全挡了**；属于 2026-10-18 单表化引入的**双闸门口径冲突**

---

## 1. 现象拆解（三种表现，一个根因）

| 用户操作 | 期望 | 实际 | 机制 |
|---|---|---|---|
| 触摸 → 只勾 `greet类` / `chat类` | 点角色播问候 / 闲聊 | **动作照播、无语音无字幕** | 漏斗抽到 `null` ⇒ `touch.playTouch` 走「池空退化」兜底，随机挑一个 `touchAnimations` 名字 |
| 待机 → 只勾 `touch类` / `greet类` | 待机播触摸 / 问候 | **什么都不播** | 漏斗抽到 `null`，`tickStandby` 只 return |
| 待机 → 勾 `chat类` + `touch类` | 两类并池随机 | **只播 chat 类**（本工程只有 `game:64004` 一条） | touch 类条目被通道闸门挡掉，池里只剩 chat |
| 回到壁纸 → 勾 `chat类` / `touch类` | 回来播闲聊 / 触摸 | **什么都不播** | 同上；只有非 boot 信号会打一行 warn |

> 用户描述的「语音不播放、动作播放」精确对应**触摸通道**：这不是巧合，是 `touch.ts:1003-1010` 的空池兜底——动作有、念白没有。

## 2. 复现（无需启动 WE）

```bash
npx ts-node --transpile-only _regress/93_诊断_事件池跨类失效.ts
```

用 `public/assets/events.jsonc` 真实 15 条事件跑新旧两套取条逻辑（`rnd = () => 0` 固定取首条）：

```
standby 种类=["chat"]              | 旧池= 1 取到=game:64004 | on 可达=1 | 新漏斗=game:64004
standby 种类=["touch"]             | 旧池= 8 取到=game:64005 | on 可达=1 | 新漏斗=null
standby 种类=["chat","touch"]      | 旧池= 9 取到=game:64004 | on 可达=1 | 新漏斗=game:64004
touch   种类=["greet"]             | 旧池= 6 取到=game:64001 | on 可达=8 | 新漏斗=null
touch   种类=["chat","touch"]      | 旧池= 9 取到=game:64004 | on 可达=8 | 新漏斗=custom:headpat-soft
resume  种类=["chat"]              | 旧池= 1 取到=game:64004 | on 可达=6 | 新漏斗=null
```

「旧池」= 改动前 `pickChannelEntry` 的算法，「新漏斗」= 当前 `resolveEventFrom`。**旧实现能跨类，新实现不能**——回归成立。

## 3. 根因

### 3.1 引擎里有两层筛子，方向相反

```
① 通道闸门  channelsOf(e).indexOf(channel) >= 0     ← 条目 on 必须包含本通道
② 类别筛子  kinds.indexOf(kindOf(e, channel)) >= 0  ← 条目 kind 必须在用户勾选里
```

`src/eventScheduler.ts:362-367`。① 是 2026-10-18 单表化新加的（`on` 字段落地），
② 才是「事件池」页那三行多选真正对应的东西。旧实现**只有 ②**：

```ts
// 2d979be^ 的 index.ts（已删除）
const pickChannelEntry = (kinds) => {
  ...
  return pickRandomFromPool(mergeKindPools(kinds, KIND_POOLS, fams));  // 无通道判断
};
```

⇒ 从前「待机勾 touch 类」= 从触摸池取条；现在 = 触摸池的条目一条都过不了待机闸门。

### 3.2 数据侧把「类别」这个轴冻死了

`events.jsonc` 里 15 条内置事件**每条只写一个通道，且与 kind 一一对应**：

```
on:["resume"] + kind:"greet"   ×6
on:["standby"] + kind:"chat"   ×1
on:["touch"]  + kind:"touch"   ×8
```

这不是手写的，是 `scripts/migrateEvents.ts` 用 `normalizeEventTable` 反推后序列化的结果：
旧 config 的三个池（`touch` / `chat` / `greeting`）**本来只表达类别**，迁移时被 1:1 映射成了通道。
于是"类别"和"通道"两根本该正交的轴被焊成一根——用户再怎么勾，能落地的只有"同通道同类别"那一格。

**这是真正的设计缺陷**：`on` 的语义应是"作者允许它在哪些通道被取"，`kind` 才是类别；旧池从来没有表达"这条只能点击触发"的意思。

### 3.3 为什么完全静默（四处都不吭声）

1. `resolveEventFrom` 抽不到只返回 `null`，不打日志（`collectCandidates` 无任何输出）；
2. `resolveTriggerKinds` 的"可用性"判据（`hasChat/hasGreet/hasTouch`）只看**类别池**长度，不看通道可达性 ⇒ `standbyKinds` 里明明有 `touch`，面板与探针都显示"可用"；
3. 触摸通道把 `null` 兜底成"随机动画名"⇒ 看起来"点得动"，只是没声音；
4. `eventValidate.ts` 的 16 个码里**没有**"kind 被勾选但通道不可达"这一项，档案页与启动日志都不会报。

## 5. 为什么测试没拦住

- `_regress/65_回归_通道事件选择.ts` 只测纯函数 `resolveTriggerIntent / normalizeTriggerKinds`，断言"touch 通道勾 chat ⇒ `['chat','touch']`"——**纯函数是对的，漏斗才错**；
- `_regress/84_回归_漏斗等价.ts` 的等价性只覆盖"自然配对"（`resume+greet` / `touch+touch`），跨类组合没有用例；
- 面板文案（"勾多类就合成一个池一起抽"）在改动后不再成立，但没有同步修订。

## 6. 修复方案

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **A（推荐）** | 内置事件 `on` 改为**全通道** `["standby","touch","resume"]`（`migrateEvents.ts` 同步改，避免重跑又写回单通道）；引擎不动 | 只改数据，不动漏斗语义；默认行为**逐字不变**（默认勾选仍只有 chat/touch/greet 各自一类）；`on` 对自定义事件仍是硬限制 | 内置事件"跨通道可播"后，用户主动勾才发生，属预期 |
| B | 漏斗放宽：`channelsOf(e).includes(channel) \|\| kinds.includes(kindOf(e))` | 一行改动 | 等于废掉 `on`；`on:[]` 孤儿条目复活；作者写 `on:["resume"]` 的限制会被用户勾选绕过 |
| C | 面板诚实化：每通道只列"该通道可达的类"，不可达置灰 + 红字 | 零歧义 | 功能变窄，"待机也播 touch 类"永远做不到 |

**推荐 A + 三处硬化**：
1. `resolveTriggerKinds` 的可用性改按"通道 ∩ 类别"算，勾了却没候选时在面板红字提示；
2. `eventValidate` 加一条 `W_KIND_UNREACHABLE`（勾了某类、但该通道一条可达都没有）；
3. `_regress/93` 转成正式回归：断言跨类组合能取到条目。

> 若采纳 A，需注意：`events.jsonc` 已部署到 WE 工程目录，改仓库版后要重新 `deployWe` 才会生效。

## 7. 决策与实施（2026-10-21，B 案）

用户拍板：**开源项目把权限放开，让开发者尽量造** ⇒ 采 B（引擎侧撤掉通道闸门），
而不是 A（数据侧把 `on` 铺成三通道）。

### 7.1 改了什么

| 文件 | 改动 |
|---|---|
| `src/eventScheduler.ts` | `channelsOf(e).indexOf(channel) < 0` → `!channelsOf(e).length`；函数头补 B 案口径 |
| `src/index.ts` | `weight:0` 启动自检不再按通道过滤（否则跨类配置会漏报） |
| `src/archive.ts` | `entriesOf(k)` 去掉"再按 `on` 过滤本通道"；触摸代表行直接用池首条；`CH_LABEL` 加「组:」前缀 |
| `src/settingsPanel.ts` | 事件开关行 `CH_TEXT` 加「组:」前缀（`on` 不再是可达性） |
| `src/eventModel.ts` | 文件头 + `channelsOf` 注释 + `W_ORPHAN` 文案改成"没有分组"口径 |
| `src/config.type.ts` | `DialogueEntry.on` 文档改为"分组 / 来源标记，不是闸门" |
| `scripts/migrateEvents.ts` | 生成的文件头注释同步（`on` 不限制入口、`priority` 全局抢戏） |
| `public/assets/events.jsonc` | 同上（注释 + 两条示例的 `note` 去掉"走 xx 通道"） |
| `agents.md` | `eventModel` / `eventScheduler` 两行注明 `on` 不是闸门 |
| `_regress/93_回归_事件池跨类.ts` | 新增 25 条断言（原诊断脚本转正） |

### 7.2 保留的三条边界（撤闸门 ≠ 全放开）

1. `on: []` 仍不可达（与 `poolOfKind`、`W_ORPHAN`、档案「不可达」同口径）——否则池/档案/漏斗三处分叉；
2. `enabled: false`（含面板开关）仍是第一道闸；
3. 想锁"只在某时机 / 某热区播"⇒ `when.ctx.signal` / `when.ctx.zone`，`on` 不再承担这个职责。

### 7.4 已知代价（写进文件头，作者需知）

`pick.priority` 是全局档位、不再按通道隔离 ⇒ 一条 `priority: 20` 的触摸事件会夺走
待机 / 问候的档位（`weight: 0` 除外）。本工程实测：待机勾 `chat+touch` 时
`custom:headpat-soft`（priority 20）会胜出。作者若想"每个入口各播各的"，
把相应条目降到同档（0）或给它加 `when`。
